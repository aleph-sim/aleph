# P5.10-01 — register-tiled fused-block kernel (`apply_kq_tiled`)

Phase 5.9 took the CUDA SV backend to Aer-GPU parity, but capped GPU gate fusion
at **width 3** (`MAX_FUSE_QUBITS = 3`). P5.9-02b had measured that the generic
`apply_kq` kernel only *profits* from fusion up to k=3; k=4,5 **regress** (down to
0.68×). The diagnosis was register spill: `apply_kq` puts one thread on a whole
2^k amplitude group, holding the block in `v[32]` / `gidx[32]` thread-local arrays
(768 B at k=5) that spill to local memory, on top of an O(4^k) dense matvec done
alone. Aer reaches its `fusion_max_qubit=5` default with register-tiled
fused-block kernels. This ticket builds ours and re-measures the sweet spot.

## The kernel

`apply_kq_tiled` (`crates/aleph-cuda/src/sv/kernels.cu`) is **warp-cooperative**:

- **One amplitude per warp lane.** A group of `dim = 2^k` *contiguous lanes*
  cooperatively owns one block; lane `sl` holds amplitude-slot `sl` in a single
  register `v`. Nothing lands in a thread-local array — no spill.
- **Matvec = intra-warp shuffle reduction.** `out[r] = Σ_c M[r][c]·v[c]` is
  computed by each lane `r` gathering `v[c]` from lane `c` via `__shfl_sync`.
  Since `dim` divides the 32-lane warp (k ≤ 5), every group is warp-local and the
  shuffles never cross a warp.
- **Matrix in shared memory.** The whole `2^k × 2^k` matrix (≤ 16 KiB at k=5) is
  loaded once per block before any divergent return, so `__syncthreads` can't
  deadlock on the partial tail block.
- **Grid = all 2^n amplitudes** (one thread each); group index `gid = tid >> k`,
  local slot `sl = lane & (dim-1)`. In-place safe (every lane reads its amplitude
  into a register before any write; the shuffle reads only registers).

Routing: `tiled_kq` (default on) + `tiled_min_k` (default **2**) — every dense
block with `k ≥ tiled_min_k` takes the tiled kernel; `with_tiled_kq(false)` forces
the generic kernel for the A/B baseline.

## Correctness

`tests/gpu_tiled_kq_oracle.rs` pins the tiled kernel **bit-for-bit against the
unfused CPU `NaiveSvBackend` at 1e-10**, forced on for every dense block
(`with_tiled_min_k(2)`), across k=2..5 — including the partial-grid-block worst
case at n=5..7 (2^n < BLOCK, so the last grid block is mostly out of range and the
shuffle mask + tail guard must still agree). k=4 and k=5 blocks are asserted
present. The existing `gpu_unitary_kq` regression stays green.

## Benchmark (RTX 4000 SFF Ada, FP64, n=28, best of 5)

A/B: the **same fused circuit**, generic `apply_kq` vs `apply_kq_tiled`, at fusion
widths k ∈ {3,4,5}. `spd` = generic(k) / tiled(k); `vs-gen-k3` = generic(k=3) /
tiled(k) — i.e. does the tiled kernel at this width beat the P5.9-02b production
baseline? (`tests/gpu_tiled_kq_bench.rs`.)

| workload    | gen-k3 (s) | k=3 spd | k=4 spd | k=5 spd | tiled-k4 vs gen-k3 | tiled-k5 vs gen-k3 |
|-------------|-----------:|--------:|--------:|--------:|-------------------:|-------------------:|
| random(d20) |    27.20   | 1.08×   | 1.11×   | 1.14×   | 1.00×              | 0.80×              |
| vqe(8L)     |    13.04   | 1.07×   | 1.13×   | 1.18×   | 0.96×              | 0.73×              |
| qaoa(p4)    |     7.77   | 1.00×   | 1.00×   | 1.00×   | 1.00× (no blocks)  | 1.00× (no blocks)  |

(qaoa's `FuseKq` produces no ≥3q blocks here — the cphase ladders collapse to a
`DiagonalPhase`, applied by `apply_phase_poly` — so it is unaffected, as expected.)

## Findings

1. **The tiled kernel strictly beats generic `apply_kq` at every width**
   (1.07–1.18×), and the margin **grows with k** (1.08 → 1.11 → 1.14 on random;
   1.07 → 1.13 → 1.18 on vqe). This directly confirms the register spill was real
   and that the tiled design removes it — the bigger the block, the more the
   generic kernel spilled, and the more the tiled kernel wins.

2. **But k=4/5 fusion still loses to k=3 fusion overall.** `tiled-k5 vs gen-k3` is
   0.73–0.80×; even `tiled-k4` only ties (1.00×/0.96×). The tiled kernel narrows
   the gap but cannot close it, because the dominant wall past k=3 is **not** the
   spill — it is the **O(4^k) matvec compute** itself. A width-5 block is a dense
   32×32 matvec per amplitude group (≈ 32 complex MACs/amplitude) vs width-3's
   8×8 (≈ 8 MACs); fusing to 5 cuts passes only from n/3 to n/5 (~1.6×) while
   quadrupling the arithmetic per amplitude. The kernel goes compute-bound and the
   fewer-passes win is overrun. This is the same shape P5.9-02b saw, now isolated:
   removing the spill leaves the compute as the binding cost.

## Outcome

- **`MAX_FUSE_QUBITS` stays 3.** The measured throughput sweet spot is unchanged;
  k=4/5 fusion regresses on dense workloads regardless of kernel. The first
  acceptance criterion (k=4,5 *beat* the k=3 baseline) is therefore **not met** —
  it is a hardware/algorithm ceiling (O(4^k) compute on one RTX 4000 Ada), not a
  kernel-implementation gap. Documented here rather than papered over.
- **The tiled kernel is the production default at k ≤ 3** (`tiled_min_k = 2`),
  worth **~1.07×** on the dense cells (random/VQE) over the old generic kernel,
  neutral elsewhere — a real, oracle-safe win on the production path, and the
  reason the kernel is not dead code.
- **The k=4,5 tiled path is correct and kept** for callers that raise the fusion
  width (or pass raw `UnitaryKq` k=4,5 blocks): there it beats generic `apply_kq`
  by 1.11–1.18×, so if a future workload or a larger card makes wide fusion pay,
  the kernel is ready.

## Why not push further on this card

Closing the k=5 gap would need the compute itself to get cheaper — e.g. exploiting
block sparsity/structure in the fused matrix (most fused blocks are far from dense
random unitaries), or FP32/TF32 tensor-core matvecs (P5.10-03 territory, a
precision change). Neither is a fused-block-kernel change; both are separate
levers. On this card, for genuinely dense width-5 blocks, n/5-vs-n/3 passes simply
don't pay for 4× the MACs.
