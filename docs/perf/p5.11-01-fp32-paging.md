# P5.11-01 — FP32 out-of-core paging → n=32 (single-GPU reach record)

The FP64 paged executor (P5.10-02, `CudaSvBackend::run_paged`) streams an **f64**
host state, so n=32 needs `2^32 · 16 B = 64 GiB` of pinned host memory — past
this box's 62 GiB host RAM. The FP32 amplitude buffer (P5.10-03) halves that:
FP32 paged n=32 is `2^32 · 8 B = 32 GiB` of pinned host, comfortably inside
62 GiB. P5.11-01 stacks the two levers to set a new **single-GPU reach record of
n=32** on the same 20 GiB RTX 4000 SFF Ada.

## What changed

A byte-for-byte FP32 mirror of the FP64 paged path:
`CudaSvBackendF32::run_paged` (`crates/aleph-cuda/src/sv/paged_f32.rs`). It holds
the `2^n` state in pinned host memory as **f32**, streams device-sized `2^m`
tiles through the GPU, and routes each co-resident tile group's compute through
the in-core FP32 kernels (`CudaSvBackendF32::apply_gate`) instead of the FP64
backend.

The tiling scheme is **unchanged** — identical high/low split, co-resident
gather, qubit remap, and `2^(h−hh)` outer iteration as P5.10-02 (see that doc for
the derivation). The `compose_high` / `high_count` helpers are reused verbatim;
only the scalar type (`f32`) and the per-tile kernels differ. Like the FP64 path,
copies are stream-ordered and synchronous (no copy/compute overlap — that is
P5.11-02), and only plain gates + barriers are supported (diagonal-phase /
tiled-block read the global index; pass an unfused circuit).

## Correctness

`tests/paged_f32_oracle.rs` forces paging on at small `n` with a small tile (so
`h ≥ 1` high bits and the cross-tile gather is genuinely exercised) and pins the
paged state against **two** references at the 1e-5 FP32 tolerance:

1. the **FP32 in-core** backend (`CudaSvBackendF32::run`) — same scalar type, so
   the only difference is data movement, not arithmetic, and
2. the exact **FP64 CPU** `NaiveSvBackend`.

Across GHZ, QFT, and random brickwall at tile sizes spanning `h ∈ {1, 2, 3}` plus
a tiny n=4 m=2 hh=2 worst case (high↔high CNOT). All pass. A norm≈1 check covers
the large-`n` `norm_sqr` streaming path.

## Reach (the headline)

`tests/paged_f32_bench.rs::paged_f32_reach_n32`, RTX 4000 SFF Ada (20 GiB card,
62 GiB host), GHZ n=32, tile m=27:

```
== P5.11-01 reach: n=32 (32 GiB FP32), tile m=27 ==
total 182.73s, 32 gates, 5.710s/gate
effective host↔device throughput: 12.0 GB/s
norm = 1.000000 (want ≈ 1)
```

**n=32 runs on the 20 GiB card** — impossible in-core (32 GiB > 20 GiB) and
impossible for the FP64 paged path on this box (64 GiB > 62 GiB host). norm holds
at 1.000000. This is +1 qubit past the FP64 paged ceiling (n=31, P5.10-02) and
the largest exact single-GPU state aleph has produced.

## Throughput cost

`paged_f32_vs_in_core_throughput`, n=28 (fits the card both ways), one-layer
H+CNOT brick, best of 3:

| path                 | wall    | vs in-core |
|----------------------|---------|------------|
| FP32 in-core         | 0.752 s | 1.00×      |
| FP32 paged m=25 (h=3)| 19.61 s | 26.1×      |
| FP32 paged m=23 (h=5)| 19.68 s | 26.2×      |

As with the FP64 path, this is a **reach lever, not a speed lever**: at ~12 GB/s
effective the cost is PCIe-bound, the copies are serial (no overlap), and the
~26× overhead is the price of streaming the whole state through the bus per gate.
The headroom — double-buffered overlap (P5.11-02) and multi-gate tile residency
to amortise the PCIe traffic (P5.11-03) — is the rest of Phase 5.11.
