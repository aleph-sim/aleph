# Phase 5.9 — CUDA SV throughput → Aer-GPU parity

Phase 5 met its exit gate (aleph FP64 GPU SV within 1.22× of cuStateVec on every
Tier-1 + Tier-2 workload), but the P5-08 report found **Qiskit Aer-GPU is 2–5×
faster than both aleph and cuStateVec** — same FP64, its own engine (not
cuStateVec), the advantage entirely **above the kernel**: gate fusion + batched
dispatch (`docs/perf/p5-08-gpu-report.md`). Phase 5.9 closes that gap. This page
tracks it; the exit metric is in `ROADMAP.md` §7.

## P5.9-01 — feed the existing IR fusion passes into the GPU path

`fuse_for_gpu()` runs the GPU-applicable fusion sub-pipeline — `CancelInversePairs`
→ `DeadCodeElim` → `Fuse1qRuns` → `Fuse2q` — before the backend. These emit
`Unitary1q` / `Unitary2q` blocks, which the CUDA backend already applies (they
carry a `GateMatrix`, unlike `UnitaryKq`). **No new kernels.** Fewer gates ⇒ fewer
full-state passes, the dominant cost at scale.

Correctness: `tests/gpu_fusion_bench.rs::gpu_fused_matches_cpu_unfused` pins the
fused GPU run against the unfused CPU `NaiveSvBackend` at 1e-10.

### Result (RTX 4000 SFF Ada, FP64, n=28, best of 4)

| workload     | gates (before→after) | unfused (s) | fused (s) | speedup | gap to Aer-GPU |
|--------------|----------------------|------------:|----------:|--------:|---------------:|
| QFT          | 406 → 406            | 10.54       | 10.54     | 1.00×   | 1.73× (unchanged) |
| random (d20) | 1100 → 540           | 49.88       | 30.37     | **1.64×** | 2.15× → **1.30×** |
| VQE (8L)     | 664 → 242            | 29.53       | 14.42     | **2.05×** | 2.89× → **1.42×** |
| QAOA (p4)    | 476 → 138            | 22.39       | 9.02      | **2.48×** | 3.42× → **1.38×** |

The free step (no new kernels) closes most of the dense-workload gap: from 2.1–3.4×
behind Aer-GPU to **1.3–1.4×**. QFT is untouched — its controlled-phase ladder is
diagonal and doesn't collapse under `Fuse1q`/`Fuse2q`; it needs the diagonal path
below.

## P5.9-02a — apply dense `UnitaryKq` (k≤5) on the GPU

`FuseKq` (P2-07) collapses adjacent gates into dense `2^k × 2^k` `UnitaryKq`
blocks, but both CUDA SV backends *rejected* them: `UnitaryKq` has no fixed-size
`GateMatrix` (the enum stops at 8×8 / k=3), so `gate.matrix()` returns
`Unrepresentable`. The kernels themselves already handled k≤5 (`apply_kq`'s
`qbit[5]`/`sorted[5]` + a `k>5` guard; `custatevecApplyMatrix` takes arbitrary
`nTargets`).

P5.9-02a wires the two together: both backends intercept `Gate::UnitaryKq`
before validation and route the raw row-major slice through a shared
`validate_kq` + `flatten_kq` (operands MSB-first, identical to the `Unitary2q`
path). Oracle: `tests/gpu_unitary_kq.rs` runs `FuseKq{max_qubits:5}` on
dense_chain/random/vqe, applies on the GPU, and matches the unfused CPU
`NaiveSvBackend` at 1e-10 — asserting the fused circuits actually contain k=4
and k=5 blocks so the new path is exercised. **Infrastructure only; the
throughput choice is P5.9-02b.**

## P5.9-02b — feed `FuseKq` into the GPU path; width-3 is the sweet spot

`fuse_for_gpu` now appends `FuseKq{max_qubits: MAX_FUSE_QUBITS}` after
`Fuse1q`/`Fuse2q`. `FuseKq` emits a dense block only at span ≥ 3 with ≥ 2
members, so it is purely additive over P5.9-01 (isolated 1q/2q gates keep their
specialised kernels). The A/B knob `fuse_for_gpu_with(c, kq_max)` sweeps the
width (`None` = the P5.9-01 baseline).

### A/B result (RTX 4000 SFF Ada, FP64, n=28, best of 5)

Speedups are vs the P5.9-01 baseline (Fuse1q+Fuse2q, no ≥3q blocks).

| workload     | baseline gates / s | k=3 gates / s / spd | k=4 spd | k=5 spd |
|--------------|-------------------:|--------------------:|--------:|--------:|
| QFT          | 406 / 10.51        | 406 / 10.53 / 1.00× | 1.00×   | 1.00×   |
| random (d20) | 540 / 30.21        | 277 / 26.52 / **1.14×** | 1.01× | 0.78×   |
| VQE (8L)     | 242 / 14.35        | 137 / 13.05 / **1.10×** | 0.94× | 0.68×   |
| QAOA (p4)    | 138 / 8.98         |  81 / 8.32 / **1.08×**  | 0.93× | 0.71×   |

**k=3 wins 1.08–1.14× on every dense workload; k=4 and k=5 regress** (down to
0.68×). The generic `apply_kq` does a dense `2^k × 2^k` matvec per amplitude
group — O(4^k) work, 4× more at k=5 than k=3 — and its `v[32]`/`gidx[32]`
thread-local arrays (768 B at k=5) spill to local memory. Past k=3 that extra
compute overtakes the fewer-passes savings, even though gate counts keep
dropping (random: 540 → 277 → 282 → 186). So `MAX_FUSE_QUBITS = 3`. QFT is
diagonal and unaffected (no ≥3q dense runs to fuse), as in P5.9-01.

Aer reaches its k=5 default with **register-tiled fused-block kernels**; matching
that needs a kernel that keeps the `2^k` block in registers/shared memory
without spilling — a P5.9-04-class lever. Until then k=3 is the GPU sweet spot,
and the correct (oracle-pinned) k=4,5 apply path from P5.9-02a stays available
for when that kernel lands.

## Remaining levers (where the rest of the gap is)

1. **Diagonal-run fusion (QFT/QPE).** `FuseDiagonalRuns` collapses a phase ladder
   into one `DiagonalPhase` instruction (a phase polynomial over ≤64 qubits). A
   GPU kernel that evaluates `amps[x] *= exp(i·φ(x))` in one sweep — building on
   the P5-06 diagonal kernels — turns QFT's ~350 cphase passes into ~1. This is
   the single biggest lever for the diagonal half (QFT is 1.73× behind on nothing
   but pass count). → **P5.9-02**.
2. **Register-tiled fused-block kernel (unlock k=4,5).** P5.9-02a/02b shipped the
   `UnitaryKq` GPU apply path and fed `FuseKq` into the pipeline, but measured
   that the *generic* `apply_kq` only profits up to **k=3** (1.08–1.14×); k=4,5
   regress because the dense per-group matvec + register spill outgrows the
   pass-count savings. A kernel that holds the `2^k` block in registers/shared
   memory (Aer-style) is the precondition for raising `MAX_FUSE_QUBITS` toward
   Aer's 5. → **P5.9-04**-class.
3. **Disjoint-layer single-sweep dispatch.** Apply all disjoint-qubit gates of a
   layer in one pass over the state (the SV analogue of the P5-07 `stab_layer`),
   cutting both launches and sweeps. → **P5.9-03**.
4. **Specialised 2q kernels** (CNOT permutation, diagonal-2q) for the last
   1.13–1.22× vs cuStateVec. → **P5.9-04**.
