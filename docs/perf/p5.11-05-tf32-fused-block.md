# P5.11-05 — Tensor-core (TF32) fused-block matvec

P5.10-01 established that the wall past **k=3** fusion on the GPU SV is the
**O(4^k) dense matvec compute itself**, not register spill: the warp-tiled
`apply_kq_tiled` removed the `v[32]`/`gidx[32]` spill yet k=4,5 still lost to the
k=3 baseline (tiled k=5 was 0.73–0.80× generic-k3). The Ada card's **TF32 tensor
cores** (~8× the FP32 FMA rate) sat idle on that path. P5.11-05 recasts the
per-group `2^k × 2^k` complex matvec as a **batched GEMM** and runs it on the
tensor cores — the compute that gated wide fusion, made cheap.

## Approach

`apply_kq_tf32_k{4,5}` (in `kernels_tf32.cu`, a **separate NVRTC module** compiled
with `--gpu-architecture=sm_89` + the CUDA `mma.h` include path) batch **16 group
vectors** as the columns of `V` (`dim × 16`) and compute `Out = M · V` with WMMA:

- **One warp owns one 16-group tile.** It gathers the 16 group vectors into
  shared memory (col-major), runs the GEMM on the tensor cores, and scatters the
  result back. A bare per-group matvec is `N=1` — 1/16 of a 16-wide WMMA tile; the
  16-group batch runs the core near-full.
- **k=4** (dim=16) is a single 16×16 WMMA output tile, `K=16 = 2·WK` (TF32 `WK=8`).
  **k=5** (dim=32) tiles the 32×32 matrix as 2×2 of 16×16, `K=32 = 4·WK`.
- **Complex via 4 real GEMMs:** `Re = Mr·Vr − Mi·Vi`, `Im = Mr·Vi + Mi·Vr`
  (the `−Mi·Vi` term negates the a-fragment in place before accumulating into Re).
- **FP32 only.** TF32 truncates amplitudes anyway, so it pairs with the FP32
  amplitude buffer (P5.10-03 / P5.11-04); applying it to the FP64 buffer would
  downcast `f64` amps to 10-bit mantissa, defeating FP64's purpose. Routing:
  dense **k=4/k=5** blocks with no external controls (`tf32_kq`, default on) take
  precedence over the warp-tiled path; k≤3 stays tiled.

## Correctness

`tests/fp32_tf32_oracle.rs` on the RTX 4000 SFF Ada, n=12, comparing the TF32 GEMM
against the **FP32 ALU dense apply** (warp-tiled `apply_kq_tiled_f32`, forced via
`with_tf32_kq(false)`) on the *same* IR-fused circuit, and against the exact FP64
CPU `NaiveSvBackend`:

| workload     | k | Δ vs FP32-ALU | Δ vs FP64 CPU |
|--------------|---|---------------|---------------|
| random(d16)  | 4 | 7.56e-5       | 7.57e-5       |
| random(d16)  | 5 | 7.04e-5       | 7.04e-5       |
| vqe(8L)      | 4 | 7.73e-5       | 7.72e-5       |
| vqe(8L)      | 5 | 6.67e-5       | 6.67e-5       |

All within the **1e-4** TF32 acceptance budget (and the 1e-2 CPU sanity budget).
✅ acceptance criterion 1.

## Throughput

`tests/fp32_tf32_bench.rs` on the RTX 4000 SFF Ada (idle GPU), n=28, best of 5,
all paths through the `Backend` trait. Each width's TF32 GEMM is timed against the
FP32-ALU warp-tiled kernel at the same width (`spd`) and against the **production
tiled-k3 baseline** (`vs-k3`, the number the exit metric must beat):

| workload    | tiled-k3 (s) | k=4 ALU | k=4 TF32 | spd | **vs-k3** | k=5 ALU | k=5 TF32 | spd | **vs-k3** |
|-------------|-------------:|--------:|---------:|----:|----------:|--------:|---------:|----:|----------:|
| random(d20) | 10.34        | 12.58   | 10.19    | 1.23× | **1.02×** | 16.41 | 10.87 | 1.51× | 0.95× |
| vqe(8L)     | 4.55         | 6.41    | 3.84     | 1.67× | **1.18×** | 7.98  | 4.81  | 1.66× | 0.94× |
| qaoa(p4)    | 4.62         | —       | —        | —     | 1.01×     | —     | —     | —     | 1.00× |

(qaoa fuses to no dense ≥3q blocks — `≤0` — so its cells are a no-op control.)

Two findings:

1. **TF32 strictly beats the FP32 ALU at every width** — 1.23–1.67× at k=4,
   1.51–1.66× at k=5. The tensor cores *do* cut the O(4^k) matvec that P5.10-01
   named as the wall: the hypothesis holds.
2. **At k=4, TF32 finally crosses the k=3 baseline** — 1.02× (random) / 1.18×
   (VQE). k=5 narrows to 0.94–0.95× but stays under: doubling the matvec again and
   moving 32×16 tiles still outweighs the n/5-vs-n/4 pass saving. So the
   throughput-optimal TF32 fusion width is **4**.

The cross at k=4 hinged on a second lever: the first cut recomputed the
bit-insertion amp index per gathered/scattered element (`base(group) | off(local)`,
256–512× per tile). Those indices depend only on the local row (`off`) or the group
column (`base`), so precomputing each once per tile took k=4 from 0.95×/0.99× to
**1.02×/1.18×** and k=5 from 0.80×/0.77× to 0.95×/0.94×.

## Verdict

Acceptance met. The win is exposed as a **separate FP32-only fusion width**,
`MAX_FUSE_QUBITS_TF32 = 4` / `fuse_for_gpu_tf32`, **not** a bump of the shared
`MAX_FUSE_QUBITS` (3): that const also feeds the FP64 backend, which has no TF32
kernel and would route k=4 blocks to the warp-tiled ALU path where k=4 loses to k=3
(P5.10-01) — bumping it would regress FP64. Drive `CudaSvBackendF32` with
`fuse_for_gpu_tf32` to take the k=4 dense win; `tf32_kq` (default on) routes those
blocks to `apply_kq_tf32_k4`. The k=5 kernel is kept and oracle-pinned for callers
that force width 5, but the default tops out at 4.

The TF32 module is loaded **non-fatally** (`build_tf32_kernels` → `Option`): the
`sm_89` + `mma.h` NVRTC build is separate from the base FP32 module, so a host that
can't compile it (a pre-Ada card, no CUDA include dir) keeps a fully working FP32
backend — k=4/k=5 dense blocks fall back to the warp-tiled path with a one-line
warning. The lever is best-effort, never a construction-time hard dependency on
tensor-core hardware.
