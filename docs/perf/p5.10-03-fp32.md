# P5.10-03 — FP32 / mixed-precision GPU state vector

FP64 on the Ada card is compute-weak (~1/64 the FP32 rate) and the GPU SV is
memory-bandwidth bound, so storing the `2^n` amplitudes as **float** complex
halves both the footprint and the bytes moved per sweep — for ~2× throughput and
+1 qubit of in-core reach, at FP32 accuracy (~1e-5).

## Design — reuse the FP64 host path

`CudaSvBackendF32` mirrors `CudaSvBackend`'s per-gate dispatch (CNOT permutation,
fused `UnitaryKq`, diagonal fast path, dense 1q/2q/3q) but launches `*_f32`
kernels against a `2·2^n` **f32** amplitude buffer. The trick that keeps it small:

- **Gate matrices stay `f64`** inside every per-gate uniform — the CUDA structs
  are byte-identical to the FP64 `Gate1qParams` / `GateKqParams` / `CnotParams` /
  `Diag1qParams` / `DiagKqParams`, so the backend **reuses the exact same host
  param builders** (`gate_1q_params`, `gate_kq_params`, the diag builders) with
  zero duplication.
- The kernels cast each matrix coefficient to float (`cf`) at point of use, so the
  arithmetic runs on the **fast FP32 ALU**. Only the amplitude buffer is FP32 —
  which is where all the bandwidth lives.

New code is just the 5 float kernels (`kernels_f32.cu`) + a thin state/backend
(`fp32.rs`). The FP64 path is untouched.

## Correctness (1e-5)

`tests/fp32_oracle.rs` pins the FP32 final state against the exact FP64 CPU
`NaiveSvBackend` across **Tier-1** (GHZ, QFT, Grover, random) and **Tier-2** (VQE,
QAOA) at n=10 — exercising every FP32 kernel including the diagonal fast paths:

```
ghz          max |Δ| = 1.21e-8
qft          max |Δ| = 3.73e-9
grover       max |Δ| = 1.49e-8
random(d12)  max |Δ| = 3.76e-8
vqe(6L)      max |Δ| = 6.22e-8
qaoa(p3)     max |Δ| = 6.02e-8
worst across Tier-1+2: 6.22e-8  (tol 1e-5)
```

Worst error **6.2e-8** — ~160× inside the 1e-5 budget.

## Benchmark (RTX 4000 SFF Ada, 20 GiB)

### Throughput + memory (n=28, random brickwall, 1100 gates, best of 5)

```
state bytes: fp64 4096 MiB, fp32 2048 MiB  (0.50×)
fp64: 30.2933s   fp32: 14.9219s   speedup 2.03×
```

**2.03× throughput at half the memory** — exactly the bandwidth-bound prediction
(the state is the dominant traffic; halving its bytes halves the sweep time).

### Reach: n=31 in-core (+1 qubit)

```
== FP32 reach: n=31 (16 GiB in-core, FP64 would need 32 GiB) ==
total 2.447s, 31 gates, 0.0789s/gate, norm=1.000000
```

FP32 n=31 is 16 GiB and runs **in-core** on the 20 GiB card; the FP64 backend
caps at n=30 (n=31 FP64 = 32 GiB, larger than the card). Same 16 GiB budget, one
more qubit — and ~13× faster per gate than the paged n=31 of P5.10-02 (0.08 s/gate
resident vs 5.7 s/gate over PCIe), since it never leaves the card.

## Outcome — both acceptance criteria met

- **FP32 oracle-equal to FP64 within 1e-5** across Tier-1 + Tier-2 (worst 6.2e-8). ✅
- **~2× memory + throughput** (2.03× / 0.50×) and **+1 qubit reach** (n=31 in-core). ✅

## Notes

- Scope is a per-gate apply path + host-side amplitude readout — enough to run and
  pin Tier-1/2. GPU-resident readout, fusion, the register-tiled kernel (P5.10-01)
  and paging (P5.10-02) are orthogonal and can be retrofitted onto the FP32 buffer
  later if an FP32 production path warrants it.
- Combining FP32 with paging (P5.10-02) would reach n=32 in 32 GiB of pinned host
  RAM (vs 64 GiB for FP64 paged) — within this box's 62 GiB — a natural follow-up.
