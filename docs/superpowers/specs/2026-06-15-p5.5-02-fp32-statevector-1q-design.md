# [P5.5-02] FP32 statevector core + 1q kernels (Metal) — Design

> Status: approved (brainstorm 2026-06-15). Source of truth for the PR.
> Issue: #172. Milestone: Phase 5.5 — Apple/Metal GPU.
> Builds on: P5.5-01 (`aleph-metal` foundation — `MetalContext`, `DeviceBuffer<T>`,
> runtime MSL compile). Spec: `2026-06-14-p5.5-01-metal-foundation-design.md`.

## Goal

Stand up `MetalSvBackend: Backend` — a **device-resident FP32 statevector** on
Metal with a **generic single-qubit kernel**, IR-gate dispatch, and
amplitude/probability readout. This is the first physics on the GPU: it proves
the foundation can hold a statevector and apply gates correctly, validated by an
FP32 oracle against the CPU reference.

Scope is **1-qubit gates only**. 2q / diagonal / multi-controlled kernels are
P5.5-03; fused blocks P5.5-04; the perf ≥2× gate P5.5-05.

## Acceptance Criteria (from issue #172)

1. 1q circuits run on the GPU; amplitudes/probabilities readable via `AmpsF32`.
2. FP32 oracle vs `NaiveSvBackend` within `1e-5`.

## Decisions (brainstorm 2026-06-15)

- **Crate home:** `aleph-metal` (gated). The backend, state, kernels, and
  readout all live behind `cfg(all(target_os = "macos", feature = "metal"))`.
  Linux/default builds remain empty by construction.
- **Backend method scope:** *full* — `allocate`, `apply_gate` (1q),
  `measure`, `sample`, `expectation_value`, `probabilities`. The state is
  device-resident; readout/measurement run **host-side** over the
  unified-memory buffer (zero-copy on Apple Silicon).
- **Amps seam:** add an `AmpsF32` accessor (native f32 readout, mirrors the
  CLI's `AmpsF64`) *and* implement `aleph_oracle::HasAmplitudes` for the Metal
  state (widen f32→f64) so the existing oracle harness drives the comparison
  with no new harness code.
- **Readout reuse:** *reimplement locally* in `aleph-metal` (small, keeps crate
  layering clean) rather than depend on `aleph-sv` to reuse `fp32_measure`.

## Architecture

New modules inside `aleph-metal`, all gated as above. The `metal` feature gains
gated dependencies:

```toml
# crates/aleph-metal/Cargo.toml — added to the `metal` feature
[target.'cfg(target_os = "macos")'.dependencies]
aleph-backend = { workspace = true, optional = true }
aleph-core    = { workspace = true, optional = true }
aleph-ir      = { workspace = true, optional = true }
rand          = { workspace = true, optional = true }
# num-complex with bytemuck so Complex<f32>: Pod (DeviceBuffer<Complex<f32>>)
num-complex   = { workspace = true, optional = true, features = ["bytemuck"] }

[features]
metal = ["dep:metal", "dep:bytemuck", "dep:thiserror",
         "dep:aleph-backend", "dep:aleph-core", "dep:aleph-ir",
         "dep:rand", "dep:num-complex"]
```

`Complex<f32> = num_complex::Complex<f32>` is `#[repr(C)] { re: f32, im: f32 }`
— layout-identical to MSL `float2`. The `bytemuck` feature provides
`Complex<f32>: Pod`, so `DeviceBuffer<Complex<f32>>` from P5.5-01 works directly
and the kernel sees a `device float2*`. (If the num-complex `bytemuck` feature
proves awkward to wire, fall back to a local `#[repr(C)] #[derive(Pod,Zeroable)]
AmpF32 { re, im }` newtype; same layout. The feature path is preferred.)

### `MetalSvState` (`state.rs`)

```rust
pub struct MetalSvState {
    pub(crate) num_qubits: u32,
    pub(crate) amps: DeviceBuffer<Complex<f32>>, // len 2^n, unified memory
}
```

- AoS `Complex<f32>`, `amps[i]` = amplitude of `|i⟩`, MSB qubit convention
  (ADR 0004), matching every other SV backend.
- Inherent accessors: `num_qubits()`, `amplitudes_f32(&self) -> &[Complex<f32>]`
  (zero-copy `as_slice()`), `to_aos_f64(&self) -> Vec<Complex<f64>>` (exact
  widening for oracle/interop).
- Device-resident: the buffer persists across gates; only small per-gate
  uniforms upload.

### `MetalSvBackend` (`backend.rs`)

```rust
pub struct MetalSvBackend {
    ctx: MetalContext,
    pipeline_1q: ComputePipelineState, // compiled once at construction
    rng: StdRng,
}

impl MetalSvBackend {
    pub fn new() -> Result<Self, BackendError>;          // entropy seed
    pub fn with_seed(seed: u64) -> Result<Self, BackendError>;
}
```

- Construction acquires the device via `MetalContext::new()` and compiles +
  caches the 1q pipeline once. A missing device (`Error::NoDevice`) maps to
  `BackendError::InvalidState { reason: "no Metal device available" }` so
  headless callers fail explicitly (tests skip *before* constructing).
- `rng` mirrors the CPU backends for reproducible host-side `measure`/`sample`.
- Constructor returns `Result` (unlike the infallible CPU `new`) because device
  acquisition and shader compilation can fail; this is the one signature
  deviation from the CPU backends and is intentional.

Soft qubit cap: `MAX_METAL_QUBITS = 28` (project-wide software limit, matches
`Fp32SvBackend`). `allocate` rejects above it with `TooManyQubits`.

### `apply_gate` — 1q only

Validation mirrors `Fp32SvBackend::apply_gate` exactly: arity check
(`ArityMismatch`), per-qubit range (`QubitOutOfRange`) and duplicate
(`DuplicateQubit`) over `qubits ∪ controls`.

Dispatch by matrix shape:

- `GateMatrix::M2x2(m)` — narrow each entry f64→f32. **Unitarity check on the
  f64 matrix first** (`validation`-equivalent, `deviation > AMPLITUDE_TOL` ⇒
  `NonUnitaryMatrix`), defense-in-depth identical to the CPU FP32 backend. Then
  run the kernel.
- `GateMatrix::M4x4` / `M8x8` — `BackendError::UnsupportedGate { kind }`.
- `Gate::UnitaryKq { .. }` — intercept before `matrix()` (it has no fixed
  `GateMatrix`) and return `UnsupportedGate`.
- `matrix()` errors map as in the CPU backend: `SymbolicParam`,
  `NonFiniteParam`, `Unrepresentable → UnsupportedGate`.

`apply_diagonal_phase` and `apply_tiled_block` are **not** overridden — the
trait defaults apply: `apply_diagonal_phase` returns `UnsupportedInstruction`;
`apply_tiled_block` replays gates (hitting `UnsupportedGate` for any non-1q gate
in a block). `unpermute_state` is **not** overridden this ticket (no optimized
run path on GPU yet); it surfaces `UnsupportedInstruction` if reached. Oracle
tests use the raw `run` driver, so this is never hit.

### Kernel (`shaders/sv_1q.metal`)

One GPU thread per **pair**; grid size `2^(n-1)`. Uniforms packed in a
`#[repr(C)]` Pod struct bound via `set_bytes` at buffer index 1:

```metal
struct Gate1q {
    float2 m[4];      // m00, m01, m10, m11 (row-major)
    uint   target;    // target qubit index
    uint   t_bit;     // 1u << target
    uint   ctrl_mask; // control mask (0 for 1q circuits; forward-compat)
};

kernel void apply_1q(device float2* amps      [[buffer(0)]],
                     constant Gate1q& g        [[buffer(1)]],
                     uint tid                  [[thread_position_in_grid]]) {
    // Insert a 0 bit at position `target` to get the base index (target bit clear).
    uint lo = tid & (g.t_bit - 1u);
    uint hi = (tid >> g.target) << (g.target + 1u);
    uint i  = hi | lo;
    if ((i & g.ctrl_mask) != g.ctrl_mask) return;   // no-op when controls unmet
    uint j  = i | g.t_bit;
    float2 a = amps[i];
    float2 b = amps[j];
    amps[i] = cmul(g.m[0], a) + cmul(g.m[1], b);
    amps[j] = cmul(g.m[2], a) + cmul(g.m[3], b);
}
```

`cmul` is the standard complex product on `float2`
(`(x.x*y.x - x.y*y.y, x.x*y.y + x.y*y.x)`). Distinct `tid` ⇒ distinct base
index `i` (bit `target` clear) ⇒ disjoint `{i, j}` pairs ⇒ no write aliasing.

The Rust-side `Gate1q` struct mirrors this layout (`[Complex<f32>; 4]` then
three `u32`); `set_bytes` uploads it each gate. `float2` is 8-byte aligned and
the struct is naturally packed (16-byte `m`, then 3×`u32`) — no padding
surprises; an assertion pins `size_of::<Gate1q>()`.

### Dispatch & data flow (per `apply_gate`)

1. `cmd = queue.new_command_buffer()`.
2. `encoder.set_compute_pipeline_state(pipeline_1q)`.
3. `encoder.set_buffer(0, state.amps.metal_buffer(), 0)`.
4. `encoder.set_bytes(1, size_of::<Gate1q>(), &gate1q)`.
5. `dispatch_threads(MTLSize(2^(n-1),1,1), tg)` with
   `tg = pipeline.max_total_threads_per_threadgroup().min(2^(n-1))`.
6. `end_encoding → commit → wait_until_completed`.

Synchronous per gate (correctness-first). For `n == 0` (no qubits) there are no
pairs; `allocate(0)` yields a 1-element `|0⟩` and `apply_gate` cannot target a
qubit (range check rejects). Batching/lazy commit is a later perf ticket
(out of scope).

### Readout (`readout.rs`, host-side)

After the last GPU write completed (every `apply_gate` waits), the
unified-memory buffer is current. All four read paths operate on
`state.amplitudes_f32()` (`&[Complex<f32>]`):

- `probabilities(qubits)` — marginal over the requested qubits;
  `|amp|²` summed into `2^k` bins (k = `qubits.len()`), MSB convention.
- `sample(shots)` — inverse-CDF over the full `2^n` distribution using the
  backend `rng` (deterministic for a seed). A simple cumulative scan is fine at
  this scale; no alias table needed for v1.
- `measure(qubit)` — compute P(1), draw, collapse the buffer in place
  (zero the eliminated half, renormalize), write back through `as_mut_slice()`.
  `DegenerateMeasurement` when the chosen branch has ~0 probability.
- `expectation_value(pauli)` — `⟨ψ|P|ψ⟩` over f32 amps, returned as `f64`.

These mirror `fp32_measure` semantics but are reimplemented locally (small) to
avoid an `aleph-metal → aleph-sv` dependency.

### Seam: `AmpsF32` + `HasAmplitudes` (`amps.rs`)

```rust
pub trait AmpsF32 {
    fn amplitudes_f32(&self) -> &[Complex<f32>];
}
impl AmpsF32 for MetalSvState { /* zero-copy as_slice() */ }

impl aleph_oracle::HasAmplitudes for MetalSvState {
    fn amplitudes(&self) -> Vec<Complex<f64>> { self.to_aos_f64() }
}
```

`HasAmplitudes` lets the oracle test compare Metal vs the CPU reference
directly. `aleph-oracle` is a **normal optional dependency** gated behind the
`metal` feature (not dev-only): the `impl HasAmplitudes for MetalSvState` is an
external-trait impl that must live in this crate (orphan rule) and is used by
the integration oracle test, which compiles the library with `cfg(test)` off.
It is workspace-internal and feature-gated to macOS+metal, so it never weighs on
Linux/default builds. `aleph-sv` (for `NaiveSvBackend`, the f64 reference) is a
dev-dependency. `AmpsF32` is a normal public export.

## Testing

- **Unit (`backend.rs`, gated + device-guarded):**
  - `allocate(3)` → amp[0] = 1, len 8; `allocate(29)` → `TooManyQubits`.
  - H on |0⟩ → (1/√2, 1/√2) within 1e-6.
  - X, Z, S, T, Rz(θ) basis-state checks.
  - 2q gate (`Cnot`) → `UnsupportedGate`.
  Each guards on `MetalSvBackend::new()`; skip (pass) when `Err` indicates no
  device.
- **Oracle (`tests/sv_oracle.rs`):** generate random 1q circuits over
  {H, X, Y, Z, S, T, Rx, Ry, Rz, Phase, U} at n = 1..=12, seeded; run on both
  `MetalSvBackend` and `NaiveSvBackend`; assert amplitude vectors agree within
  `1e-5` via `HasAmplitudes`. Graceful skip when no device. (Reuse
  `aleph-test` strategies if they fit; otherwise a small local generator.)
- No `unwrap`/`expect` in library code; tests may `unwrap`.

## Out of scope (YAGNI)

- 2q / diagonal / multi-controlled kernels (P5.5-03).
- Fused-block `UnitaryKq` GPU kernel (P5.5-04).
- FP32 benchmark + ≥2× gate (P5.5-05).
- Batched / lazy command-buffer dispatch; offline `.metallib` precompile.
- GPU-side measurement/sampling/reduction (host-side readout is sufficient and
  correct on unified memory).
- Optimized (`run_optimized`) GPU path / `unpermute_state` override.

## Risks

- **metal-rs `set_bytes` / `dispatch_threads`:** confirmed against the pinned
  `metal` version (already used by the smoke test for `dispatch_threads`); the
  oracle is the proof they wired correctly.
- **`Complex<f32>: Pod` via num-complex `bytemuck` feature:** if the feature is
  unavailable/awkward, fall back to a local `AmpF32` Pod newtype (same `repr(C)`
  layout). Resolved at implementation time.
- **CI runner has no Metal device:** handled by design (graceful skip); GPU
  execution is proven locally and recorded in the PR description.
- **f32 accumulation at larger n:** the 1e-5 tolerance and n ≤ 12 oracle bound
  keep single-precision error well inside the gate; matches the `Fp32SvBackend`
  precedent.
