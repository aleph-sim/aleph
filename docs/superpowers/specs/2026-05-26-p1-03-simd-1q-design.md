# P1-03 — Hand-written SIMD intrinsics for 1-qubit gates (AVX2 + AVX-512)

**Issues:** P1-03 (GitHub #15) + P1-04 (GitHub #16; absorbed — see §1)
**Depends on:** P1-01 (SoA backend), [ADR 0007](../../decisions/0007-soa-x86-perf-finding.md)
**Supersedes:** P1-02 (rolled back; bit-manip pattern adopted here as SIMD inner loop)
**Date:** 2026-05-26

---

## 1. Goal

Hand-write x86 SIMD intrinsics for the generic 2×2 unitary in `SoaSvBackend::apply_1q` and prove SoA finally beats AoS on EPYC. Three code paths via runtime CPU detection:

- **AVX-512** (`__m512d`, 8 lanes f64) — top tier, EPYC bench server uses this
- **AVX2 + FMA** (`__m256d`, 4 lanes f64) — broad x86 coverage (Haswell 2013 +)
- **Scalar fallback** — keeps the P1-01 flat predicate-loop shape (LLVM auto-vec already extracts the relevant work — per ADR 0007)

This ticket **absorbs P1-04** (GitHub #16). The original P1-03/P1-04 split into "AVX2 then AVX-512" was artificial: the two paths share the same kernel structure, differing only in lane count and intrinsic prefix (`_mm256_*` vs `_mm512_*`). Implementing them together avoids two rounds of shared-infrastructure churn. ARM NEON is **deferred** to a follow-up ticket.

The acceptance bar is the same as the merged BACKLOG P1-03 entry: **`qft/n20/soa` ≥ 2× faster than P1-01 SoA on the EPYC bench server**. The post-P1-02-rollback EPYC baseline (commit `07d3724`, same-load measurement) is `qft/n20/soa = 332 ms`. Target: ≤170 ms. Stretch: also beat `qft/n20/naive ≈ 250 ms` (AoS auto-vec'd AVX-512), which finally validates the SoA layout decision.

## 2. Scope

### In scope

- Three implementations of generic 2×2 unitary `apply_1q` in `crates/aleph-sv/src/kernels/soa/{scalar,avx2,avx512}.rs`
- Runtime dispatcher in `crates/aleph-sv/src/kernels/soa.rs::apply_1q` (public signature unchanged from P1-01)
- AVX-512 / AVX2 inner loop uses nested block/pair indexing (the P1-02 pattern, finally meaningful because SIMD `vmovupd` consumes the unit-stride inner block)
- Controlled-gate path: hoist sort of `(target, controls)` once outside the loop into a stack-only `SmallVec<[(u32, bool); 8]>`, then call `expand_with_fixed(k, &sorted_fixed)` per outer block; inner SIMD walk unchanged
- Sub-vector-target tail handling: when `target_bit < lane_count`, the SIMD path falls through to the next lower tier (AVX-512 → AVX2 → scalar) so kernels never read out of bounds
- Per-path test surface: `apply_1q_scalar` / `apply_1q_avx2` / `apply_1q_avx512` accessible to tests via `pub(crate)` for forced execution on capable hosts
- Bench: existing `crates/aleph-sv/benches/soa_vs_naive.rs` captures the SIMD effect; PR body reports EPYC bencher.dev numbers post-CI

### Out of scope (deferred)

- **ARM NEON** — separate follow-up (`apply_1q_neon`). Apple silicon auto-vec on SoA is already close to AoS parity locally; NEON intrinsics offer a smaller marginal win than AVX-512 does on EPYC.
- **Specialised Pauli-X SIMD kernel** — P1-05 (cross-lane swap pattern, not a 2×2 matrix multiply)
- **Specialised diagonal-gate SIMD kernel** — P1-06 (lane-wise phase multiply, simpler than generic 2×2)
- **2-qubit SIMD** — P1-07 (4×4 matrix application, needs different lane orchestration)
- **3-qubit SIMD** — out of P1 perf scope (Toffoli/CCZ are rare; oracle equivalence is enough)
- **AoS path** — `kernels::aos::apply_1q` untouched. Auto-vec already extracts AVX-512 packed-double; LLVM does the work. (Touching it risks regressing the AoS reference.)
- **`SoaSvBackend::apply_gate`, `measure_soa`, `validation`, `soa_state`, oracle harness** — no changes. The substitution is internal to `kernels::soa::apply_1q`.

### 3.2 Dispatcher

```rust
// kernels/soa.rs
pub(crate) fn apply_1q(
    re: &mut [f64],
    im: &mut [f64],
    target: u32,
    controls: &[u32],
    m: &[[Complex; 2]; 2],
) {
    debug_assert_eq!(re.len(), im.len());
    debug_assert!(re.len().is_power_of_two());

    #[cfg(target_arch = "x86_64")]
    {
        // `is_x86_feature_detected!` caches into a static AtomicU32 after first
        // call; per-dispatch cost is one atomic load. Acceptable at apply_gate
        // granularity (microseconds per call).
        if std::is_x86_feature_detected!("avx512f") {
            // SAFETY: feature check confirms the ISA is available.
            unsafe { soa::avx512::apply_1q(re, im, target, controls, m); }
            return;
        }
        if std::is_x86_feature_detected!("avx2") && std::is_x86_feature_detected!("fma") {
            unsafe { soa::avx2::apply_1q(re, im, target, controls, m); }
            return;
        }
    }
    soa::scalar::apply_1q(re, im, target, controls, m);
}
```

The dispatcher is the **only public hot-path symbol**. `SoaSvBackend::apply_gate` continues to call `crate::kernels::soa::apply_1q(...)` unchanged.

## 4. Scalar fallback (`kernels/soa/scalar.rs`)

**Verbatim move of the P1-01 `apply_1q` body** — no behaviour change. The ADR 0007 finding is that LLVM auto-vectorizes this shape on x86 (masked-loop with `vp*q` index ops + 16 vmulsd matrix muls), and on ARM auto-vec via NEON gets us close to AoS parity. This is the right scalar code.

```rust
//! Scalar SoA apply_1q fallback. Compiles to ~16 vmulsd + 8 vporq
//! (masked-loop vectorization) on x86-64 with -C target-cpu=native; ARM
//! NEON auto-vec yields a similar packed-double shape. Per ADR 0007:
//! do NOT replace this with a bit-manip restructure — that pessimizes
//! LLVM's masked-loop transformation.

use aleph_core::Complex;

pub(crate) fn apply_1q(
    re: &mut [f64],
    im: &mut [f64],
    target: u32,
    controls: &[u32],
    m: &[[Complex; 2]; 2],
) {
    debug_assert_eq!(re.len(), im.len());
    let t_bit = 1usize << target;
    let ctrl_mask = crate::kernels::control_mask(controls);
    let len = re.len();
    let mut i = 0usize;
    while i < len {
        if i & t_bit == 0 && (i & ctrl_mask) == ctrl_mask {
            let j = i | t_bit;
            let a0_re = re[i];
            let a0_im = im[i];
            let a1_re = re[j];
            let a1_im = im[j];
            re[i] = m[0][0].re * a0_re - m[0][0].im * a0_im
                + m[0][1].re * a1_re - m[0][1].im * a1_im;
            im[i] = m[0][0].re * a0_im + m[0][0].im * a0_re
                + m[0][1].re * a1_im + m[0][1].im * a1_re;
            re[j] = m[1][0].re * a0_re - m[1][0].im * a0_im
                + m[1][1].re * a1_re - m[1][1].im * a1_im;
            im[j] = m[1][0].re * a0_im + m[1][0].im * a0_re
                + m[1][1].re * a1_im + m[1][1].im * a1_re;
        }
        i += 1;
    }
}
```

## 5. AVX2 path (`kernels/soa/avx2.rs`)

`__m256d` = 4 lanes f64. Process **4 pairs per inner iteration**: one vec for `re[i0..i0+4]`, one for `im[i0..i0+4]`, one for `re[i1..i1+4]`, one for `im[i1..i1+4]`. Apply 2×2 via broadcasts + FMA.

### 5.1 Uncontrolled fast path (`controls.is_empty()`)

```rust
use core::arch::x86_64::*;
use aleph_core::Complex;

const LANES: usize = 4;

#[target_feature(enable = "avx2,fma")]
pub(crate) unsafe fn apply_1q(
    re: &mut [f64],
    im: &mut [f64],
    target: u32,
    controls: &[u32],
    m: &[[Complex; 2]; 2],
) {
    let target_bit = 1usize << target;
    let len = re.len();

    // Broadcast matrix entries to 4-lane vectors (constant across all iterations).
    let m00r = _mm256_set1_pd(m[0][0].re);
    let m00i = _mm256_set1_pd(m[0][0].im);
    let m01r = _mm256_set1_pd(m[0][1].re);
    let m01i = _mm256_set1_pd(m[0][1].im);
    let m10r = _mm256_set1_pd(m[1][0].re);
    let m10i = _mm256_set1_pd(m[1][0].im);
    let m11r = _mm256_set1_pd(m[1][1].re);
    let m11i = _mm256_set1_pd(m[1][1].im);

    if controls.is_empty() {
        // Pure nested block/pair. Each block has target_bit pairs.
        let outer_step = target_bit << 1;
        let mut block = 0usize;
        while block < len {
            apply_block_4(re, im, block, target_bit,
                          m00r, m00i, m01r, m01i, m10r, m10i, m11r, m11i, m);
            block += outer_step;
        }
    } else {
        // Controlled: hoist sort once.
        let mut fixed: smallvec::SmallVec<[(u32, bool); 8]> = smallvec::SmallVec::new();
        fixed.push((target, false));
        for &c in controls { fixed.push((c, true)); }
        fixed.sort_unstable_by_key(|(pos, _)| *pos);
        let n_qubits = len.trailing_zeros();
        let outer_count = 1usize << (n_qubits - fixed.len() as u32);
        for k in 0..outer_count {
            let block = crate::kernels::expand_with_fixed(k, &fixed);
            apply_block_4(re, im, block, target_bit,
                          m00r, m00i, m01r, m01i, m10r, m10i, m11r, m11i, m);
        }
    }
}

#[target_feature(enable = "avx2,fma")]
#[inline]
unsafe fn apply_block_4(
    re: &mut [f64], im: &mut [f64], block: usize, target_bit: usize,
    m00r: __m256d, m00i: __m256d, m01r: __m256d, m01i: __m256d,
    m10r: __m256d, m10i: __m256d, m11r: __m256d, m11i: __m256d,
    m: &[[Complex; 2]; 2],
) {
    let mut j = 0usize;
    while j + LANES <= target_bit {
        let i0 = block | j;
        let i1 = i0 + target_bit;

        // SAFETY: i0+LANES ≤ block + target_bit ≤ block + target_bit ≤ len
        //         (block stride is 2*target_bit, so block + target_bit ≤ len).
        let re0 = _mm256_loadu_pd(re.as_ptr().add(i0));
        let im0 = _mm256_loadu_pd(im.as_ptr().add(i0));
        let re1 = _mm256_loadu_pd(re.as_ptr().add(i1));
        let im1 = _mm256_loadu_pd(im.as_ptr().add(i1));

        // new_re0 = m00r*re0 - m00i*im0 + m01r*re1 - m01i*im1
        // Express as FMA: (m00r*re0) + (m01r*re1 - m00i*im0 - m01i*im1)
        // Use fmsub_pd(a,b,c) = a*b - c.
        let new_re0 = {
            let t1 = _mm256_fmsub_pd(m00r, re0, _mm256_mul_pd(m00i, im0));
            let t2 = _mm256_fmsub_pd(m01r, re1, _mm256_mul_pd(m01i, im1));
            _mm256_add_pd(t1, t2)
        };
        // new_im0 = m00r*im0 + m00i*re0 + m01r*im1 + m01i*re1
        let new_im0 = {
            let t1 = _mm256_fmadd_pd(m00r, im0, _mm256_mul_pd(m00i, re0));
            let t2 = _mm256_fmadd_pd(m01r, im1, _mm256_mul_pd(m01i, re1));
            _mm256_add_pd(t1, t2)
        };
        // new_re1 = m10r*re0 - m10i*im0 + m11r*re1 - m11i*im1
        let new_re1 = {
            let t1 = _mm256_fmsub_pd(m10r, re0, _mm256_mul_pd(m10i, im0));
            let t2 = _mm256_fmsub_pd(m11r, re1, _mm256_mul_pd(m11i, im1));
            _mm256_add_pd(t1, t2)
        };
        // new_im1 = m10r*im0 + m10i*re0 + m11r*im1 + m11i*re1
        let new_im1 = {
            let t1 = _mm256_fmadd_pd(m10r, im0, _mm256_mul_pd(m10i, re0));
            let t2 = _mm256_fmadd_pd(m11r, im1, _mm256_mul_pd(m11i, re1));
            _mm256_add_pd(t1, t2)
        };

        _mm256_storeu_pd(re.as_mut_ptr().add(i0), new_re0);
        _mm256_storeu_pd(im.as_mut_ptr().add(i0), new_im0);
        _mm256_storeu_pd(re.as_mut_ptr().add(i1), new_re1);
        _mm256_storeu_pd(im.as_mut_ptr().add(i1), new_im1);

        j += LANES;
    }
    // Tail: leftover pairs (j..target_bit). For `target ≥ 2` this is 0;
    // for target = 0 (target_bit = 1) it's 1; for target = 1 it's 3.
    // Apply scalar matrix multiply to the remaining pairs.
    while j < target_bit {
        let i0 = block | j;
        let i1 = i0 + target_bit;
        let a0_re = re[i0];
        let a0_im = im[i0];
        let a1_re = re[i1];
        let a1_im = im[i1];
        re[i0] = m[0][0].re * a0_re - m[0][0].im * a0_im
            + m[0][1].re * a1_re - m[0][1].im * a1_im;
        im[i0] = m[0][0].re * a0_im + m[0][0].im * a0_re
            + m[0][1].re * a1_im + m[0][1].im * a1_re;
        re[i1] = m[1][0].re * a0_re - m[1][0].im * a0_im
            + m[1][1].re * a1_re - m[1][1].im * a1_im;
        im[i1] = m[1][0].re * a0_im + m[1][0].im * a0_re
            + m[1][1].re * a1_im + m[1][1].im * a1_re;
        j += 1;
    }
}
```

### 5.2 Performance shape

Per AVX2 inner iter:
- 4 vector loads (`_mm256_loadu_pd`)
- 4 vector stores (`_mm256_storeu_pd`)
- 8 mul + 8 FMA = 16 vector arithmetic ops → equivalent to 64 scalar muls/adds
- Compared to scalar 16 vmulsd per 1 pair: **16× theoretical throughput per pair, 4× per cycle from packed lanes**

For `target=10` on `n=20` qubits (typical QFT mid-target): each block has 1024 pairs, all fit in 256 AVX2 iterations. Outer block count = 2^9 = 512. Inner SIMD utilisation ~100% (1024 % 4 == 0 → zero tail).

For `target=0`: 1 pair per block, all tail, zero SIMD. Falls back to scalar tail handler effectively. P1-03 should still net even because the dispatch overhead is < 10 ns and AVX2 hot path is the main contribution at typical targets.

## 6. AVX-512 path (`kernels/soa/avx512.rs`)

**Structurally identical to AVX2**, with:
- `__m512d` instead of `__m256d` (8 lanes f64)
- `_mm512_*` intrinsics
- `#[target_feature(enable = "avx512f")]`
- `LANES = 8`

Sub-vector-target fallback: when `target_bit < 8` (i.e. `target < 3`), the AVX-512 path delegates the inner block to **the AVX2 implementation** (which itself handles `target_bit < 4` via scalar tail). This keeps the AVX-512 main loop free of tail-handling code; the AVX2 path is already correct and well-tested.

Concretely:

```rust
#[target_feature(enable = "avx512f")]
pub(crate) unsafe fn apply_1q(re, im, target, controls, m) {
    let target_bit = 1usize << target;
    if target_bit < 8 {
        // Sub-512-bit target: hand off to AVX2 path (which handles up to 4 lanes
        // and falls back to scalar tail). Faster than a 1-of-8 masked store.
        return crate::kernels::soa::avx2::apply_1q(re, im, target, controls, m);
    }
    // Otherwise: 8-lane SIMD with same block/tail shape as AVX2.
    // ... (mirror of §5.1 with __m512d)
}
```

This avoids implementing masked stores via `__mmask8` for the small-target case. The cascade is: AVX-512 main → AVX2 main → scalar tail.

## 7. Controlled path correctness

The controlled-gate path computes `block` differently from the uncontrolled path. After `expand_with_fixed(k, &sorted_fixed)`, `block` has:

- `target_bit` clear in `block` (by construction — `(target, false)` in fixed)
- Every control bit set in `block` (by construction — `(c, true)` in fixed)

But: **the inner SIMD loop walks `j ∈ 0..target_bit` and reads `re[block | j]`**. For this to be valid (all controls set in `block | j`), `j` must not toggle any control bit. Since `j < target_bit` and `target_bit < 1 << min(controls)`... wait — not generally true.

Concretely: if `target = 5` and `controls = [2]`, then `target_bit = 32` and `control_bit = 4`. Inner loop walks `j ∈ 0..32`. When `j == 4`, `block | j` toggles the control bit (which `expand_with_fixed` set to 1) — wrong.

**Fix:** the inner loop must only walk `j` values that **don't touch any fixed bit other than target**. Since `expand_with_fixed` already places `block`'s free bits in the non-fixed positions, the safe `j` range walks the free bits below `target`, then jumps past `target_bit`, then walks free bits up to the next fixed position.

The clean form: factor out `low_target_bit = lowest_fixed_bit_strictly_above_block_padding`. Actually the most general clean form is to walk *the lowest-target free-bit block* — i.e. when `target` is the **lowest fixed bit**, inner is contiguous `0..target_bit`; otherwise, walk the contiguous free-bit block immediately below the lowest fixed bit (which may be a control, not target), and have an outer-outer loop over the remaining higher-position fixed-bit layout.

This is fiddly. **Simpler design**: for the controlled SIMD path, only vectorize when **`target` is the lowest fixed bit** (i.e. `target < min(controls)`); otherwise fall through to scalar. This guarantees `j ∈ 0..target_bit` touches no control bits.

Coverage check for QFT-20:
- QFT layer at qubit `q` applies H on q, then controlled-Phase(angle) with control `c > q` (control bit always higher than target). So `target < min(controls)` holds for every controlled-Phase in QFT. ✓
- Grover diffusion: same shape. ✓
- General circuit: not guaranteed. Fall through to scalar; correctness preserved.

This is a deliberate scope cut — covers the hot QFT path, defers the general case. Document it explicitly:

```rust
// In the controlled SIMD path, before computing `outer_count`:
if controls.iter().any(|&c| c < target) {
    // Lowest fixed bit is a control, not target. SIMD inner loop would
    // toggle control bits; fall back to scalar path (correct, slow).
    return crate::kernels::soa::scalar::apply_1q(re, im, target, controls, m);
}
```

Cost: 1 comparison per apply_gate call for controlled gates. Negligible.

## 8. Safety boundary

The `unsafe` surface is **strictly the `#[target_feature]` function bodies**. The dispatcher and scalar fallback are entirely safe Rust.

Invariants the AVX2 / AVX-512 bodies rely on:
1. `re.len() == im.len()` (debug_assert in dispatcher)
2. `re.len()` is a power of two (debug_assert in dispatcher)
3. `target < re.len().trailing_zeros()` (caller — `SoaSvBackend::apply_gate` — validates qubit range)
4. `controls` contains no element equal to `target` (caller validates via `DuplicateQubit` check)
5. For every `c` in `controls`, `c < re.len().trailing_zeros()` (caller validates qubit range)
6. Inner block loop: `j + LANES ≤ target_bit` → reads `re[block + j .. block + j + LANES]` and `re[block + target_bit + j .. block + target_bit + j + LANES]`; both spans lie within `[block, block + 2*target_bit)`, which is `≤ re.len()` because the outer loop steps by `2*target_bit` and stops at `len`.

SAFETY doc-block on every `unsafe fn` enumerates these, with `// SAFETY:` comments at each `_mm*_loadu_pd` / `_storeu_pd` call site referencing the relevant invariant.

`unsafe` is also required for `#[target_feature]` regardless of body safety. We use the pattern `pub(crate) unsafe fn apply_1q(...)` and have the safe dispatcher do the feature check + wrap the call.

## 11. Risks and mitigations

| Risk | Mitigation |
|---|---|
| `unsafe` bug in SIMD body (out-of-bounds load, wrong intrinsic) | Workhorse equivalence + per-path proptest + boundary unit tests catch any divergence within 1e-12. SAFETY doc-block at each `_mm*_loadu_pd` cite the relevant invariant from §8. |
| Sub-vector-target tail handler off-by-one | Dedicated unit tests for `target = 0, 1, 2` (AVX2) and `target = 0..=3` (AVX-512). |
| Controlled path with `control < target` produces wrong results | Explicit fall-through to scalar (§7), unit test exercises that path. Proptest covers both control orientations. |
| `std::is_x86_feature_detected!` macro per-call cost regresses dispatch | Macro caches into `static AtomicU32` after first call; per-call cost is one atomic load (~1 ns). Negligible at apply_gate granularity (µs-scale). |
| EPYC AVX-512 hand-roll doesn't beat LLVM AVX-512 auto-vec on AoS | PR ships if P1-01 SoA AC met (≥ 2× over P1-01 SoA). Document the AoS-AVX-512-auto-vec finding in the PR body; consider whether to flip the default backend to AoS for x86. |
| Build fails on non-x86 (ARM Apple silicon dev) | `#[cfg(target_arch = "x86_64")]` gates all SIMD code and dispatcher branches. Scalar path is the only one compiled on ARM; correctness via auto-vec there. |
| `#[target_feature]` ABI subtleties (caller must also have feature) | Tests must call the `unsafe fn` from inside a `#[target_feature]` context OR via the safe dispatcher. We use the dispatcher in tests where possible; for forced-path testing, callers add the appropriate `#[target_feature]` (test-only code in same crate). |
| LLVM lowers `_mm256_loadu_pd` worse than expected on some chips | Bench numbers from EPYC CI runs determine merge; if a regression appears vs P1-01 SoA, investigate via `objdump --no-show-raw-insn` per ADR 0007 workflow. |
| AVX2 path target = 0 ("all tail") regresses vs scalar | Dispatch unit test on `target = 0` ensures correctness; benchmark unit on `n=10, target=0` confirms perf. If regression measured, dispatcher should fall through to scalar for `target_bit < LANES` instead of using the SIMD path. |

## 14. Implementation order

1. **`kernels/soa/scalar.rs`** — extract P1-01 `apply_1q` body verbatim into the new file; `kernels/soa.rs::apply_1q` becomes a trivial wrapper calling `scalar::apply_1q`. No behaviour change. Workhorse + 112 oracle stay green.
2. **`kernels/soa.rs` dispatcher skeleton** — add the `#[cfg(target_arch = "x86_64")]` block, but with both branches calling `scalar::apply_1q`. Compiles on ARM (only sees scalar). Compiles on x86 (dispatcher present but paths empty).
3. **`kernels/soa/avx2.rs` — uncontrolled fast path** — implement `apply_1q` for `controls.is_empty()` only; controlled path stub falls back to `scalar::apply_1q`. Wire into dispatcher. Run workhorse + per-path proptest restricted to `n_ctrls = 0`.
4. **`kernels/soa/avx2.rs` — controlled path with `control > target` guard** — add the hoist-sort + `expand_with_fixed` loop; control-below-target fall-through to scalar. Extend proptest to `n_ctrls ∈ 0..=2`.
5. **AVX2 boundary unit tests** — target = 0, 1, 2 on small `n`; controls above and below target.
6. **`kernels/soa/avx512.rs` — full implementation** — mirror of AVX2 with `__m512d`; sub-target fallback to AVX2 (§6). Wire into dispatcher above AVX2. Workhorse + AVX-512 proptest + boundary tests.
7. **Workspace fmt / clippy / full test sweep** — ensure no warnings under `-D warnings`.
8. **Bench locally on M-series** — confirm scalar path numbers unchanged (sanity).
9. **Push branch; verify CI** — bench job on EPYC reports numbers; PR body captures EPYC table.
10. **BACKLOG ACs tick** — flip `[ ]` → `[x]` for P1-03 entry; revise "5 gate types" to "generic 2×2 unitary" in same edit; mark P1-04 entry as `**DEFERRED, FOLDED INTO P1-03**` (same pattern as P1-02 entry post-rollback).
11. **PR body final** — paste EPYC bench table, list affected files, note P1-04 absorbed.
