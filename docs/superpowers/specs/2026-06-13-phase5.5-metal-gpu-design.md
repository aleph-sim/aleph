# Phase 5.5 — Apple/Metal GPU backend (design)

**Status:** design approved 2026-06-13 — **queued after the CPU phases** (Phase 4.6
work, then the deferred Phase-3 follow-ups). No implementation starts until the
CPU track is done. Bootstrap artifact: ROADMAP row + §7 metric + BACKLOG
`P5.5-01…07` + milestone + GitHub issues (this PR).

## Why

GPU work (Phase 5 = CUDA/cuQuantum) is blocked on NVIDIA hardware the project
doesn't have. Apple Silicon (Metal) is available *now* (dev Mac + an M4-base Mac
Mini, 24 GB unified). A Metal backend lets the project make real GPU progress
on-hand, and — since there is **no established Metal quantum-circuit-simulator
reference** — the honest experiment is a clean same-box comparison: aleph's own
CPU path vs the Metal path on identical hardware. Framing: aim to be a first-mover
QC simulator on Metal; the *theoretical* win is on compute-heavy fused paths,
while pure statevector is bandwidth-bound (the project has shown this on CPU) and
that ceiling is itself a worthwhile documented result.

This is a **side-track**, not the distributed-multi-GPU vision (that stays Phase 6,
Distributed). Architecture work here (device buffer model, kernel dispatch) is
partially reusable by a future CUDA Phase 5; the Metal kernels are not.

## Decisions (from brainstorming, 2026-06-13)

1. **Placement:** fractional **Phase 5.5 — Apple/Metal GPU** (matches the 4.5/4.6
   convention; GPU sibling after Phase 5 CUDA, before Phase 6 Distributed). Chosen
   over integer "Phase 6 + bump Distributed→7" to avoid renumbering 6 live
   `[P6-xx]` distributed issues + their milestone. Number is incidental — work
   happens after the CPU phases regardless.
2. **Scope:** **FP32 statevector + *start* MPS-on-Metal.**
3. **Precision:** **FP32 only** — Apple Silicon GPUs have no `double` in Metal.
   Oracle tolerance is **1e-5** (the P2-08 FP32-CPU regime), never the FP64 1e-10.
4. **Exit bar:** `MetalSvBackend` **≥2× the same-Mac CPU statevector** on ≥2 Tier-1
   workloads at **n≈28**, FP32 oracle 1e-5 vs Aer green; honest-ceiling clause if
   bandwidth-capped. Defensible even on base M4 (~120 GB/s): the CPU baseline is
   the Mac's NEON/scalar path (no AVX-512), and CPU cores typically can't saturate
   the unified-memory bandwidth the GPU can.
5. **Benchmark box:** **M4-base Mac Mini, 24 GB (~120 GB/s)** (dev possibly moved
   onto it for a stretch). 24 GB unified → GPU addressable ~16–18 GB → SV cap
   ~n=30–31 at FP32.

## Architecture

- **New crate `aleph-metal`** hosting two `Backend` implementors: `MetalSvBackend`
  (FP32 statevector) and `MetalMpsBackend` (FP32 MPS, "started"). Both consume the
  existing IR — no Metal concern leaks into `aleph-core`/`aleph-ir` (Golden Rule
  #4).
- **Binding: the `metal` crate** (gfx-rs/`metal-rs`, mature pure-Rust Metal
  bindings). Kernels in **MSL** (`.metal`).
- **Hard build isolation:** the crate compiles only under
  `cfg(target_os = "macos")` **and** a non-default `metal` cargo feature. The
  default workspace build and all Linux/EPYC CI never touch it — existing CI stays
  green unchanged. A **macOS CI leg** builds `--features metal`.
- **Device seam (modest, not a premature HAL):** a thin internal
  `MetalContext` (device, command queue, `.metallib`) + `DeviceBuffer<T>` over
  `MTLBuffer` on unified memory (zero-copy host views — no PCIe staging). Kept
  clean and *informed by* a future CUDA port, but not abstracted cross-vendor now
  (YAGNI; CUDA is a separate phase).
- **MSL build:** `build.rs` precompiles `.metal` → `.metallib` via
  `xcrun metal/metallib` at build time (deterministic, fails fast; CLT is always
  present on macOS). Runtime source-compile only as a fallback.
- **FP32 boundary:** IR/gates stay FP64 (`Complex=c64`); convert to FP32 **at
  upload** (gate matrices → `f32×2`, state in `f32`). Add an **`AmpsF32`** accessor
  to the backend seam (mirroring the existing `AmpsF64`/`HasAmplitudes`) so
  oracle/CLI read FP32 amplitudes and compare against the FP64 reference at 1e-5.
  CLI `--backend metal` implies FP32.

## Tickets (P5.5-01 … 07)

1. **P5.5-01 — Metal foundation + build/CI plumbing.** `aleph-metal` skeleton:
   `metal` dep, `cfg(macos)`+`metal`-feature gate, `MetalContext`, `DeviceBuffer`,
   `build.rs` metallib precompile, macOS CI leg building `--features metal`, one
   trivial smoke kernel proving end-to-end dispatch. *(Toolchain spike promoted to
   a foundation ticket — working dispatch before any physics.)*
2. **P5.5-02 — FP32 statevector core + 1q kernels.** `MetalSvBackend: Backend`
   (device-resident FP32 state), |0…0⟩ alloc, generic 1q kernel, IR-gate dispatch,
   amplitude/probability readout via `AmpsF32`. FP32 oracle vs `NaiveSvBackend`
   (1e-5) for 1q circuits.
3. **P5.5-03 — 2q / diagonal / multi-controlled kernels.** CNOT/CZ/SWAP/generic-2q,
   diagonal-phase, Toffoli/MCX. Full Tier-1 (GHZ/QFT/Grover/random) on GPU. FP32
   oracle vs **Aer** (1e-5).
4. **P5.5-04 — Fused-block (`UnitaryKq`) GPU kernel.** Reuse the existing IR fusion
   passes to apply a fused k-qubit block as one kernel (fewer state passes, more
   arithmetic per byte). The lever most likely to clear ≥2×.
5. **P5.5-05 — FP32 oracle harness + Tier-1 benchmark + the ≥2× gate.** Reusable
   FP32 (1e-5) oracle vs Aer-on-Mac + criterion `MetalSvBackend` vs same-Mac CPU SV
   at n≈28 on the M4 base. SV exit measurement; honest-ceiling reporting if
   bandwidth-bound.
6. **P5.5-06 — MPS-on-Metal scaffold ("start").** `MetalMpsBackend`: site tensors
   on device, GPU kernels for the 2-site contraction + gate-apply, NN-2q.
   **SVD-gap decision: SVD on CPU (faer) via the unified-memory round-trip
   initially, document the sync cost; GPU-SVD deferred to a follow-up.**
7. **P5.5-07 — Phase 5.5 perf report + exit gate.** Consolidated M4-base report (SV
   ≥2× verdict, MPS-start status, FP32 ceiling characterization), ROADMAP §7
   Phase-5.5 exit metric, phase status flip.

## Correctness & testing

- **FP32 regime:** oracle tolerance **1e-5**. Oracles: `MetalSvBackend` vs Aer
  statevector and vs `NaiveSvBackend`; proptest invariants (normalization,
  unitarity) at FP32 tol.
- **CI:** macOS leg *builds* `--features metal`; correctness tests *run* on the
  macOS runner if its Apple GPU is usable, else `#[ignore]` + run on the dev Mac /
  M4 Mini. **Perf is never gated in CI** — measured only on the M4 base.

## Exit metric (ROADMAP §7, Phase 5.5)

`MetalSvBackend` ≥2× same-Mac CPU statevector on ≥2 Tier-1 @ n≈28 (M4 base) with
FP32 oracle 1e-5 vs Aer green; MPS-on-Metal scaffold runs NN circuits correct
(1e-5) with the CPU-SVD round-trip documented; honest-ceiling clause if SV is
bandwidth-capped.

## Risks

- **FP32-only** — cannot meet the FP64 1e-10 regime; all Metal validation is the
  1e-5 FP32 oracle. Decisive, accepted.
- **Bandwidth ceiling on base M4** — pure SV may not clear ≥2×; the fused-block
  kernel (P5.5-04) is the hedge, and the honest-ceiling clause covers a structural
  miss (cf. P3-13).
- **No external Metal etalon** — comparison is same-box CPU + Aer-CPU only; weaker
  validation story than the Aer/Stim matrix, accepted as inherent to first-mover.
- **MPS SVD gap** — Metal Performance Shaders has matmul but no SVD; the "start"
  scope uses CPU SVD via unified-memory round-trip, GPU-SVD deferred.
- **macOS CI GPU availability** — GitHub macOS runners may not expose a usable GPU;
  fall back to `#[ignore]` + local runs on the M4 Mini.
