# [P2-08] Optional FP32 (single-precision) state-vector mode — Design

**Issue:** #108 · **Milestone:** Phase 2 · **Branch:** `p2-08-fp32-mode`
**Date:** 2026-06-03

## Goal

Add an opt-in single-precision (`Complex<f32>`) state-vector backend that halves
bytes-moved per gate. P2-05 established that the Tier-1 kernels are
DRAM-bandwidth-bound at large `n`; `Complex<f32>` is 8 B/amplitude vs 16 B for
`Complex<f64>`, a direct ~2× cut in memory traffic and therefore ~1.5–2×
wall-clock where streaming dominates, traded against accuracy (~1e-6 vs ~1e-10).

FP64 stays the default and the 1e-10 oracle-reference path — **untouched**. FP32
is an explicit large-`n` performance mode, matching Qiskit Aer's
`precision: single`.

## Acceptance Criteria (from BACKLOG §[P2-08])

1. Opt-in FP32 mode; FP64 remains default and unchanged.
2. ~1.5–2× wall-clock vs FP64 on a bandwidth-bound workload at `n ≥ 24` (EPYC),
   reported in the PR.
3. Oracle equivalence vs Qiskit Aer single-precision within **1e-5** amplitudes;
   FP64 oracle path untouched.

## Decisions (brainstorm forks resolved)

| Fork | Decision | Why |
|------|----------|-----|
| Generic `T: Float` vs dedicated backend | **Dedicated `Fp32SvBackend`** | The ~11.5k lines of kernels are hand-written AVX-512 f64 intrinsics (`__m512d`/`_pd`). Intrinsics are **not** generic over float type, so a generic path would still have to monomorphize them by hand — no DRY win — while risking the f64 hot path. A separate backend isolates f64 completely. |
| Kernel coverage | **f32 AVX-512 for fused hot-types only + scalar f32 fallback for all gates** | After the P2-06/P2-07 fusion pipeline, `run_optimized` collapses circuits into a small set of fused gate types. SIMD only those; scalar-f32 covers every other gate for correctness. AC #2 measured on `run_optimized`. |
| Layout | **AoS only** (no f32 SoA) | AoS won the SIMD layout question in P1-03/ADR 0008; SoA-f32 would be dead code for the hot path. |
| Mode selection | **CLI `--precision {f64,f32}`** (clap, default `f64`) | Matches Aer's `precision`; `Fp32SvBackend` implements the `Backend` trait so the oracle/run harness works unchanged. |
| AC bench workload | **Builder QFT-25** (`qft_scaling`) | Canonical bandwidth-bound bench from P2-01..05 (3.37×@8); comparable to prior reports; cphase-ladder is the cleanest bytes-moved demo. |
| `UnitaryKq` SIMD bound | **`k ≤ 4`** (current `FuseKq` default `max_qubits`), `k = 5` → scalar | Matches the f64 dispatch; k5 is already slower in f64 (P2-07), so no f32 SIMD value. |

## Architecture

### New components (all in `aleph-sv`)

```
crates/aleph-sv/src/
├── fp32_state.rs        # Fp32CpuState { num_qubits, amps: AlignedBuf<Complex<f32>> }
├── fp32_backend.rs      # Fp32SvBackend: Backend (State = Fp32CpuState)
└── kernels/
    └── aos_f32.rs       # f32 kernels: scalar (all gates) + AVX-512 (fused hot-types)
```

FP64 files (`state.rs`, `backend.rs`, `kernels/aos.rs`, `kernels/soa.rs`,
`soa_state.rs`, `soa_backend.rs`) are **not modified** beyond, at most, additive
`pub(crate)` exports of shared index-math helpers if reuse is cleaner than
duplication (a judgment call left to the plan; correctness-preserving either
way).

### `Fp32CpuState`

Mirror of `CpuState` with `AlignedBuf<Complex<f32>>`:

- `AlignedBuf<Complex<f32>>` works unchanged — the POD contract
  (`const { assert!(!needs_drop && !ZST) }`) holds for `Complex<f32>` (8 B, Copy).
- `allocate`: `AlignedBuf::<Complex<f32>>::zeroed_state(dim)`, then
  `amps[0] = Complex::new(1.0f32, 0.0)`. NUMA first-touch (`numa` feature) reused
  via the same `zeroed_state`/`zeroed_first_touch` dispatch.
- Read-only getters `num_qubits()`, `amplitudes() -> &[Complex<f32>]`.
- `to_aos_f64() -> Vec<Complex<f64>>` widening helper for oracle/interop paths
  (FP32 result widened to f64 before comparison; the 1e-5 tolerance accounts for
  the single-precision accumulation error).

### `Fp32SvBackend`

Implements `aleph_backend::Backend` with `type State = Fp32CpuState`. The trait
surface is 7 methods — all implemented for f32: `allocate`, `apply_gate`,
`measure`, `sample`, `expectation_value`, `probabilities`, and
`apply_diagonal_phase`. `DiagonalPhase` is **not** a `Gate` variant; it is an
`aleph_ir::Instruction::DiagonalPhase` applied through the dedicated
`apply_diagonal_phase(&self, state, &aleph_ir::DiagonalPhase)` method (the
default trait impl returns `Unsupported`, so f32 must override it — same as the
f64 backends). Same shape as `NaiveSvBackend`: seeded/entropy RNG, arity checks,
dispatch in `apply_gate` to `kernels::aos_f32`. Soft qubit cap higher than f64
(`Complex<f32>` is half the
bytes: 2^29 × 8 B = 4 GiB → `MAX_FP32_QUBITS = 29`), but the project software cap
of 28 still bounds it; documented in the plan.

Measurement/sampling: reuse the existing `measure`/`sampling` logic adapted to
f32 amplitudes (probabilities computed in f64 to avoid catastrophic
cancellation in the norm sum — accumulate `|amp|²` as f64).

### Kernels (`kernels/aos_f32.rs`)

**f32 AVX-512** (`__m512` / `_ps`, 16 lanes/zmm vs 8 for f64), feature-gated by
`is_x86_feature_detected!("avx512f")`, for the fused hot-types that
`run_optimized` emits:

| Gate variant | f32 SIMD kernel | f64 analogue mirrored |
|--------------|-----------------|------------------------|
| `Gate::Unitary1q` (dense) | `apply_1q_f32_avx512` | `aos::apply_1q_avx512` |
| `Gate::Unitary1qDiag` | `apply_1q_diag_f32_avx512` | `aos::apply_1q_diagonal_avx512` |
| `Gate::Unitary2q` (dense) | `apply_2q_f32_avx512` | `aos::apply_2q_avx512` |
| `Gate::UnitaryKq { k ≤ 4 }` | `apply_kq_f32_aos` | `unitary_kq::apply_kq_aos` |
| `DiagonalPhase` | `apply_diagonal_phase_f32_aos` | `diagonal_phase::apply_diagonal_phase_aos` |

**Scalar f32** for *every* gate type (including X/Y/CNOT/CZ/SWAP/Toffoli/CCZ/MCX
and the fused types as fallback) — straight type-substituted mirrors of the
existing `*_scalar` f64 kernels. Guarantees correctness on any circuit and on
non-AVX-512 hardware (local aarch64 dev runs scalar only).

**Parallelism:** reuse `par_blocks` / `par_units` (P2-01) with a new
`ComplexF32Ptr` (a `#[derive] Copy` `*mut Complex<f32>` wrapper with `unsafe
impl Send + Sync`) mirroring the existing `ComplexPtr`. Same chunk-policy
plumbing (P2-04) — default grain, the f64 sweep found no headroom.

**SIMD math correctness note:** the AVX-512 complex-multiply lane layout
(real/imag interleave, FMA chains) for f32 mirrors the f64 kernels exactly but
with 16-lane `__m512`. The block-disjointness invariant from P1-07
(`block | offsets[k] | j` pairwise-disjoint bits) applies identically;
`LANES_F32 = 8` complex amplitudes per zmm (16 f32 scalars). Low-bit tiers
(`c < log2(LANES_F32)`) need the same renormalised outer-walk guards as f64.

### Mode selection (CLI / API)

- `aleph-cli`: add `--precision {f64,f32}` (clap `ValueEnum`, default `f64`).
  `exec.rs` constructs `Fp32SvBackend` when `f32`, else the current backend. The
  `f64` path is byte-for-byte unchanged.
- Library: `Fp32SvBackend` exported from `aleph-sv` lib root alongside
  `NaiveSvBackend` / `SoaSvBackend`.

## Data flow

```
circuit ──optimize() [P2-06/07 pipeline]──▶ fused IR
   │                                            │
   └─ run_optimized(&mut Fp32SvBackend, …) ─────┘
        per fused gate ─▶ Fp32SvBackend::apply_gate
                              ├─ avx512 available & fused hot-type ─▶ f32 AVX-512 kernel
                              └─ else ─▶ scalar f32 kernel
        ─▶ Fp32CpuState (Complex<f32> amps)
            ─▶ measure/sample (probs accumulated in f64)
            ─▶ to_aos_f64() for oracle compare @ 1e-5
```

## Testing

1. **Property (proptest)** in `aleph-sv`: normalization (‖ψ‖² = 1 within ~1e-5)
   and unitarity (random gate sequences preserve norm) on `Fp32CpuState`.
2. **Internal equivalence:** Tier-1 fixtures run on both `Fp32SvBackend` and
   `NaiveSvBackend`; amplitudes agree within ~1e-5 (FP32 tolerance). Mirrors the
   `all_fixtures_match_naive` workhorse.
3. **Oracle vs Aer single-precision:** new oracle path comparing `Fp32SvBackend`
   to Qiskit Aer `precision='single'` within **1e-5**. The existing FP64 1e-10
   oracle suite must still pass unchanged (regression guard on AC #1).
4. **SIMD ≡ scalar:** f32 AVX-512 results bit-comparable (within f32 ULP
   tolerance) to f32 scalar on indexing-coverage fixtures — the
   integer-reproduction coverage test pattern from P1-07/P1-05 (catches low-bit
   tier and external-control index bugs that kernel tests miss).
5. **Bench:** `qft_scaling` (builder QFT-25) f32 vs f64 on EPYC via
   `run_optimized`; report the ratio in the PR. Thread-invariance guard (results
   independent of rayon thread count) as in P2-05.

## Validation ops

- SIMD builds/tests only exercise on x86_64 — validate f32 AVX-512 on EPYC
  ([[aleph-bench-server]]); local aarch64 runs scalar only.
  `cargo check --target x86_64-unknown-linux-gnu` checks SIMD codegen locally.
- Deliver to EPYC via git bundle; idle-check before benching
  ([[feedback-check-server-clean]]); clean up clone+bundle after.

## Out of scope (YAGNI)

- f32 SoA backend (AoS-only decision).
- f32 ports of the specialized non-fused AVX-512 kernels (X/Y/CNOT/CZ/SWAP/
  Toffoli/CCZ/MCX) — scalar f32 covers them; the optimized path doesn't emit
  them.
- `f16`/`bf16` (mentioned in the `Complex<T>` alias rustdoc as a future GPU
  possibility) — not this ticket.
- Python bindings precision flag (Phase 4+).
