## Goal

Phase-5.5's **statevector exit measurement**. Deliver two reusable artifacts plus a
verdict:

1. **Part A** — a Metal **FP32 correctness oracle** that runs `MetalSvBackend`
   through the committed exact-FP64 Qiskit-Aer fixtures and asserts agreement
   within `1e-5` on Tier-1.
2. **Part B** — a criterion **bench** comparing `MetalSvBackend` against the
   same-Mac CPU statevector (both FP32 and FP64) on Tier-1 at `n~28`.
3. **Part C** — a **verdict doc** section: either ≥2× on ≥2 Tier-1 workloads, or a
   documented structural-ceiling verdict.

### Acceptance criteria (from #175)

- [ ] FP32 oracle vs Aer green on Tier-1 (`1e-5`).
- [ ] `MetalSvBackend` ≥ 2× same-Mac CPU SV on ≥ 2 Tier-1 @ `n~28` (M4 base) **OR**
  a documented structural-ceiling verdict if bandwidth-capped.

### Execution split

The dev box is an **M3 MacBook Air, 16 GB**. The user owns an **M4-base Mac Mini**
and will run all on-device tests + the bench there. This repo work produces the
harness, the bench, the doc scaffold, and an implementation plan with exact Mini
commands. CI is unchanged: perf is never gated, and the Metal tests are
device-or-skip so headless/Linux CI stays green.

## Background: how "oracle vs Aer" already works

The oracle is **fixture-based**, not live. `oracle/fixtures/*.json` hold exact
**FP64 Qiskit-Aer** statevectors generated offline by `oracle/gen.py` (qiskit venv
at `oracle/.venv`, python 3.11). `aleph_oracle::run_state_oracle_with_tol(backend,
fixture, qasm, tol)` parses the matching QASM, runs it through a `Backend`, and
asserts each amplitude matches the fixture within `tol`. `Fp32SvBackend` already
uses this at `FP32_STATE_TOLERANCE = 1e-5`; comparing a single-precision backend
against the *exact* FP64 reference at 1e-5 bounds the f32 accumulation error
against the true answer — strictly stronger than "vs Aer single-precision."

The existing Metal oracle (`crates/aleph-metal/tests/sv_oracle.rs`) compares
`MetalSvBackend` against `NaiveSvBackend` (aleph's own FP64 CPU), and only for
random **1q** circuits. P5.5-05 adds the genuine **vs-Aer** Tier-1 path.

## Part A — Metal FP32 Aer oracle

**File:** `crates/aleph-metal/tests/sv_oracle_aer.rs` (new; sibling of
`sv_oracle.rs`, same device-or-skip idiom).

- Loads the committed Tier-1 fixtures and their QASM from `oracle/fixtures` /
  `oracle/circuits` (paths anchored via `CARGO_MANIFEST_DIR`), and for each, runs
  `MetalSvBackend` through `aleph_oracle::run_state_oracle_with_tol(.., 1e-5)`.
- **Tier-1 coverage** from fixtures already present:
  - GHZ: `ghz_3`, `ghz_5`, `ghz_10`
  - QFT: `qft_3`, `qft_5`
  - Grover: `grover_2q_mark11`, `multi_ctrl_grover_ccz_3q`
  - Random: `random_clifford_n4_d20`, `random_nonclifford_n4_d20`
- Runs **both** `run` (gate-by-gate) **and** `run_optimized` (fused `apply_kq`
  path) through the oracle for every fixture, so the exact code path the n~28
  bench times (`run_optimized`) is the one proven correct.
- **Device-or-skip:** if `MetalSvBackend::with_seed(0)` returns `Err` (no Metal
  device), print a skip line and return — keeps Linux/headless CI green.
- The oracle stays at **small n by design**: a 2^28 Aer JSON fixture is multi-GB
  and absurd. Correctness *at scale* is Part B's self-consistency guard.

If the existing small-n fixtures feel thin, `oracle/gen.py` can mint a couple more
(e.g. `qft_8`, `ghz_16`) on the Mini, but the listed set already exercises all
four Tier-1 families and is sufficient for "green on Tier-1."

## Part B — Tier-1 GPU-vs-CPU exit bench

**File:** `crates/aleph-metal/benches/sv_vs_cpu.rs` (new; modeled on
`sv_fused.rs`). Registered in `crates/aleph-metal/Cargo.toml` as a second
`[[bench]]` with `harness = false`, `required-features = ["metal"]`.

**Arms (3), all on the same default-optimized IR pipeline** (`run_optimized`) so
the comparison is backend-only:

| Arm | Backend | Precision |
|-----|---------|-----------|
| `gpu`     | `MetalSvBackend`   | FP32 |
| `cpu_f32` | `Fp32SvBackend`    | FP32 (apples-to-apples) |
| `cpu_f64` | `NaiveSvBackend`   | FP64 (headline CPU SV) |

**Workloads & sizes.** Tier-1 builders from the `aleph-benches` crate (`benches/`):
- `ghz_circuit(n)` — alloc/bandwidth-bound (1 H + chain of CNOTs).
- `qft_circuit(n)` — H + controlled-phase ladder.
- `random_brickwall_circuit(n, depth)` — densest 2q structure; the strongest GPU
  case. Modest `depth` (≈20) to keep n=28 wall-time tractable.
- n-sweep `{24, 26, 28}`; **n=28 is the headline cell**. The sweep lets a 16 GB
  Mini stop before it thrashes.
- **Grover is excluded from the n=28 sweep.** Its multi-controlled decomposition
  is enormous and Grover-25 is already ~13 CPU-h single-thread (memory:
  `p2-05-merged`). Include one Grover cell at a smaller n (≈20, from
  `scripts/qiskit-baseline/circuits/grover_n20_iters5.qasm`) as an extra GPU-vs-CPU
  data point, not in the headline sweep.

**Correctness guard at scale (required).** There is no Aer fixture at n=28, so a
fast-but-wrong kernel could otherwise "pass" the bench. Before the timed loop, for
each (workload, n) the bench runs the circuit once on `gpu` and once on
`NaiveSvBackend`, and asserts a **sampled** set of amplitudes (e.g. a fixed stride
+ the few largest-magnitude indices) match within `1e-5`. Only then does it bench.
This guarantees the timed GPU work is correct, not just fast.

**Bench mechanics (per P5.5-04 lessons).**
- Backends are built inside `iter_with_setup`'s **untimed** setup closure, so
  pipeline compile / construction is untimed; the zero-state `allocate` runs
  inside `run_optimized` and is therefore timed — but identically across all
  arms, so ratios are unaffected.
- Each arm is a separate criterion group/benchmark so only one large CPU buffer is
  live at a time. **Memory at n=28:** GPU FP32 buffer ≈ 2.15 GB, `cpu_f32` ≈
  2.15 GB, `cpu_f64` ≈ 4.30 GB. Peak ≈ one FP64 buffer + overhead → safe on 16 GB.
  Metal `maxBufferLength` on a 16 GB Mini comfortably exceeds 2.15 GB.
- Reduced `--sample-size` (≈10–20) and explicit warm-up/measurement times because
  n=28 samples are seconds-long.

**Run command (Mini):**
```
cargo bench -p aleph-metal --features metal --bench sv_vs_cpu
```

- **Both verdict branches pre-written**, user keeps the one their data supports:
  1. **≥2× met** — name the ≥2 Tier-1 workloads and ratios.
  2. **Structural-ceiling verdict** — the integrated GPU shares **unified-memory
     bandwidth** with the CPU, so a bandwidth-bound statevector cannot reach the
     discrete-GPU 2×. Back it with the measured GPU≈CPU ratio and the
     memory-bandwidth argument, consistent with the Phase-2 bandwidth-wall
     findings (`docs/perf/phase2.md`).

and hardware line; all prose is complete so the user just drops in measurements.

## Out of scope / non-goals

- No new kernels or backend changes — pure test + bench + doc (like P5.5-04).
- No new IR passes; reuse the existing default-optimized pipeline.
- No live Aer at test time; fixtures are the Aer reference.
- No CI changes; perf stays non-gating, Metal tests stay device-or-skip.
