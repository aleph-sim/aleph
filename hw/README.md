# `hw/` — sim-first FPGA decoder track (Phase Q6)

The North Star of the QEC track is a real-time decoder on hardware (FPGA → ASIC). The board (a
**Xilinx Kria KV260**) is being procured; this directory starts the work **in simulation** so the
RTL, testbench, and host↔hardware data flow are ready and verified before the board arrives.
Simulation is Mac-native (Verilator); synthesis (Vivado) targets the KV260 and runs on an x86 Linux
box later.

## What's here

Two decoders as synthesisable RTL, each verified in simulation against its Rust reference:

| file | role |
|------|------|
| `surface_d3_decoder.sv` | **Q6-01:** d=3 surface-code memory-Z decoder — an 8-bit syndrome indexes a 256-entry ROM → 1-bit correction, 1-cycle valid/valid handshake (the "syndrome-in / correction-out skeleton"). |
| `surface_d3_lut.mem` | its ROM — **generated by the Rust Union-Find decoder** (`crates/aleph-qec/examples/qec_d3_lut_table.rs`). |
| `tb_surface_d3.cpp` | Verilator TB: all 2^8 syndromes vs the Rust oracle + latency. |
| `uf_rep_decoder.sv` | **Q6-02 (stepping stone):** repetition-code **Union-Find / minimum-weight** decoder — a *real datapath* (prefix-XOR network + popcount + min-coset select), not a ROM. Outputs the full correction + logical flip, 1-cycle latency. |
| `tb_uf_rep.cpp` | Verilator TB: all 2^(D-1) syndromes — checks the correction **reproduces the syndrome** and the logical flip **matches the Rust `UnionFindDecoder`** (`qec_rep_uf_vectors.rs`). |
| `Makefile` | regenerate the reference tables, build with Verilator, run. |

## Run it

```bash
brew install verilator        # one-time (macOS)
make -C hw                    # build + run both decoders
make -C hw rep                # just the Union-Find decoder
```

Expected:
```
PASS: 256/256 syndromes match oracle; decode latency = 1 clock(s)
PASS: 64/64 syndromes valid + match Rust UF oracle; decode latency = 1 clock(s)
```

## Why a lookup table first, then a datapath

A full syndrome→correction table is exponential in the detector count, so the d=3 LUT (Q6-01) is only
a *flow* proof: a Rust-derived decoder turned into RTL and verified bit-exactly, with a clean
streaming interface and a measured latency. **Q6-02** replaces it with a real **Union-Find** datapath.
The repetition-code core here is the 1-D specialisation (on a line, UF cluster growth = minimum-weight
matching = the prefix-XOR / min-coset computation in `uf_rep_decoder.sv`); the **2-D surface-code
cluster-growth UF** (grow / union / peel) is the next increment, behind the same interface.

## Roadmap

- **Q6-01:** sim-first toolchain + d=3 LUT decoder skeleton, Verilator-verified. ✅ (sim)
- **Q6-02:** Union-Find datapath — repetition-code core ✅ (sim); 2-D surface-code cluster-growth UF
  next; then synthesise for the KV260 and measure on-board latency.
- **Q6-03:** GPU (Q3-01) vs FPGA latency/throughput/power report.

The board self-programs from its on-board ARM Linux; Vivado (x86-Linux only) builds the bitstream.
See `docs/qec/ROADMAP.md` §8 and the project memory for hardware specifics.
